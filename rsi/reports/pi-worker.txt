MEMORY AT EVERY PROVIDER REQUEST
- The RSI extension subscribes to context_with_system and calls the external
  MemoryPort on every request. It uses injectMemoryAtRequestBoundary from shared:
  one leading system message, latest content in the named "memory" section,
  all later system messages folded/replayed by getCurrentSystemMessage.
- The provider payload is captured by the faux provider, not by helper strings.
  Tests prove: same-run tool update -> next provider request contains the new
  Memory in system position; old Memory is absent; the human prompt marker is
  replayed once and unchanged; empty Memory removes the old content; a native
  retry request contains Memory that changed after the first attempt.
- Memory is never inserted as user/assistant/tool history. Assistant tool-call
  arguments can contain text the model wrote, but no injected Memory message is
  added outside system.
- before_agent_start is not used for Memory. Reload/continuation/compaction paths
  all reach the same context_with_system hook. Compaction-triggered summary calls
  themselves were not separately measured.

TOOL RESULT FINALIZATION
- Top-level tool results are finalized in message_end for role toolResult. This is
  necessary because Pi's unknown-tool, argument-validation, blocked and aborted
  immediate outcomes do not reach tool_result/afterToolCall.
- Nested calls are finalized in tool_result and keep details, structuredContent
  and usage. Their finalized content is recorded and visible to the parent.
- Because the current payload uses content replacement, tool_result for top-level
  calls does not rewrite content; message_end preserves usage/details/nestedCalls/
  durationMs/isError and appends a text block after images.
- Decoration is exactly once, keeps images, and uses the shared order:
  index report, Memory usage (only on a successful Memory update), index warnings,
  then (Current Time: YYYY/MM/DD HH:mm:ss) at call end.
- Tests cover native read/write/edit/bash, a mounted custom tool, web_search,
  sleep, pi_control, a nested read, unknown tool, validation failure, blocked
  call, image result, truncation details, custom usage/details/structuredContent,
  and index warning on every result. read(index.md) report is model-visible and
  the on-disk index is unchanged; read counts are recorded externally.

MANAGED KNOWLEDGE
- The native definitions remain in use. Only managed direct *.md children of

- Memory.md writes go through docs.commit with revision CAS; the Memory usage

SLEEP AND CONTROL
- sleep accepts exactly one of duration (s/m/h positive integer) or until
  (YYYY/MM/DD HH:mm:ss). Both/neither/zero/fraction/past are validated.
- The tool requests the external SleepGate, waits with timers, emits sleep.entered/
  sleep.woke, and returns a model-visible result. context_with_system checks the
  external sleep status again before every provider request, covering the native
  automatic tool loop, continuation and queued follow-up. Heartbeat is an
  independent interval and continues while sleeping.
- Tests assert there is no early provider call for the tool sleep or for an
  externally active sleep, and that a retry/continuity run settles only once.
- SessionControlGuard patches the public AgentSession methods and the bindings:
  setModel, setThinkingLevel, cycleModel, shutdown and session replacement
  commands are unavailable to active extensions/agents. Tests exercise those API
  calls through a real extension and verify AGENT_COMMAND_FORBIDDEN and unchanged
  model/thinking. Normal extension commands and native tools remain registered.
- pi_control supports status and forwards reload as a request to an injected
  external RuntimeControlPort; it does not call session.reload inside the active
  run. shutdown/cancel_sleep are rejected for the active agent.
- Every reload entry exercised reaches worker.requestReload -> external
  reload.preflight -> external reload.started -> real session.reload:
  extension command context reload, direct session.reload, and trusted IPC
  control.reload. New extension tools registered by the approved replacement
  become active and callable. A failed preflight does not run session.reload.

RESOURCE DISCOVERY AND CAPS
- The ResourceLoader wraps native DefaultResourceLoader. noExtensions=true and
  approved additional extension paths prevent global/project/package extension
  directories from bypassing the approved immutable set. Skills/prompts/themes/
  context files still follow native global/project/package/discovered discovery.
- Skills are counted from the final discovered Skill objects, not a settings array.
  Tests cover global, trusted project, a local package manifest, and
  resources_discover. Five load; a sixth fails startup without slicing. Untrusted
  project skills are not loaded.
- MCP config uses Pi's native global/project merge and trust. Config + dynamic
  registrations are counted as one namespace before activation. Five start; six
  are an explicit RESOURCE_CAP_EXCEEDED. pi.registerMcpServer is capped before
  registry mutation/connection; a sixth returns an error and the registry stays 5.
- The built-in MCP extension factory (createMcpExtension) is included along with
  codemode/tool_search, preserving the native MCP initialization path. Tests use
  disabled HTTP servers, so no real MCP transport/auth is exercised.

HEALTH, SETTLEMENT, TELEMETRY
- session.subscribe distinguishes agent_end from agent_settled. Health is recorded
  only at agent_settled via the awaited extension handler, with assistant count,
  stopReason and aborted. Native retry and pi-continuity continuation each produce
  one health turn and one agent_settled; agent_end is not treated as final idle.
- run() refuses to start while a previous run/retry/continuity settlement is active.
  Tests verify a single external prompt produces two provider requests but one
  settlement and one health turn.
- Heartbeat reports sequence/pid/generation/state/healthTurns/memoryRevision and
  keeps running during sleep. Exceptions go to an optional telemetry sink; the
  Supervisor contract still needs an external event/method for them.
- A replacement AgentSession is rebound through replaceSession: guard, health
  listener, decoration and extension bindings are reinstalled; test verifies.
