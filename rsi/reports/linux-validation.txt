BWRAP VERSION / --disable-userns VERIFICATION

The source requirement is inspectBubblewrapRuntime() in
rsi/src/sandbox/preflight.ts: bwrap must be non-setuid, expose
--disable-userns, pass a real user/PID/IPC/UTS/mount namespace probe as the
distinct Worker UID, have no supplementary groups, and report CapEff=0. The
deployment preflight was updated to call that same inspector instead of using a
weaker shell probe.

Version facts checked against upstream/package data during this change:

- Docker Hub tag node:22.19.0-trixie-slim exists (observed last_updated
  2025-09-09 in the Docker Hub API).
- Debian bookworm has bubblewrap 0.8.0-2+deb12u1.
- Upstream bubblewrap v0.8.0 bwrap.xml contains --disable-userns. So the option
  is present in the bookworm package, but the task requirement was not to assume
  that by repository name.
- Debian trixie has bubblewrap 0.12.0-1~deb13u1. Inspecting the published
  trixie amd64 .deb in this snapshot showed /usr/bin/bwrap mode 0755 (not
  setuid) and package sysctl advice to enable kernel.unprivileged_userns_clone.
- Upstream 0.12.0 includes the openat2/symlink sandbox-setup security fix; 0.11.2
  includes the setuid-mode CVE-2026-41163 fix. Debian security data lists
  bookworm as older/vulnerable for the newer CVE-2026-87766 line.
- Therefore the image base was moved from node:22.19.0-bookworm-slim to
  node:22.19.0-trixie-slim rather than relying on an unverified old package.

rsi/Dockerfile now fails the build unless the installed bwrap:
  - is executable and not setuid/setgid,
  - advertises --disable-userns and --unshare-user in `bwrap --help`,
  - prints a version,
  - has setpriv and newuidmap present,
  - and Node 22.19 can execute the TypeScript Supervisor entry
    (`node /opt/rsi/src/main.ts --help`).

This build-time check was NOT executed in this snapshot because Docker is
unavailable. It is not a substitute for the real namespace probe on the target.

TARGET SUITE COVERAGE

The target suite is designed to run only inside the real Linux image with real
bubblewrap and the test-mode faux provider. It covers:

1. Clean /data and /state volumes: expect-empty assertion, first baseline
   generation, real Worker pid/health/watchdog state.
2. Sandbox filesystem protection using the actual Worker bash/Node tools:
   manual system prompt, Memory/index markdown, RSI code, Pi source, active
   immutable candidate, parent rename, symlink alias, /proc/self/root,
   /proc/1/root, retained file descriptor, nested user namespace, and bind mount.
3. proc/fd/alias/caps/PID: isolated /proc, host Supervisor pid hidden, nested
   userns denied, CapEff=0, distinct UID/GID, namespace PID different from host
   bwrap PID, Watchdog records the host bwrap PID.
4. Broker update visibility: the Supervisor atomically replaces Memory while a
   sandboxed Worker loop reads the same read-only directory mount; the new bytes
   become visible without restarting the Worker.
5. Static syntax rejection and 3-second Mock-load timeout for a while(true)
   candidate; neither reaches a real reload or changes the active digest.
6. A valid reload that registers a real tool, calls it after loading, then keeps
   the exact generation/digest through three healthy turns and promotes that
   same digest to external LKG.
7. A post-reload delayed crash and a post-reload event-loop hang. Each must be
   killed/restarted by the Watchdog, restore the exact external LKG digest, and
   deliver the recovery notice in the first recovery turn.
8. Explicit sleep: sleeping health with a future deadline, sleeping heartbeat,
   Worker crash/restart during sleep, original deadline preservation, one prompt
   wake after the deadline, and post-wake recovery notice.
9. Persistence across restart: the suite also exercises a Supervisor restart
   with the same paths, and linux-validation.mjs then performs an actual
   two-container restart on the same /data and /state volumes. Read statistics
   and a pending recovery notice must survive and be served by the second
   container.
10. The pinned web_search plugin uses only a local mock HTTP endpoint under the
    real Worker. No external provider is contacted.

No test writes a production prompt or Memory. The prompt is a temporary fixture
("TARGET-VALIDATION-HUMAN-PROMPT-FIXTURE") mounted read-only and removed with
the test directory. The target suite does not inject markdowns/operations or
security documentation into the Agent system.

HOST / DEPLOYMENT PREREQUISITES (FAIL CLOSED)

Before Linux/Docker acceptance can pass:

1. Linux host with a working Docker daemon and permission for the invoking user
   to build/run containers.
2. Kernel unprivileged user namespaces enabled for the container
   (user.max_user_namespaces > 0; distro-specific userns switch if present).
3. fs.protected_hardlinks=1 and fs.protected_symlinks=1 on the host kernel.
4. Docker custom seccomp support and rsi/deploy/seccomp-bwrap.json accepted by
   the installed Docker/libseccomp version.
5. On AppArmor hosts, the container profile must allow the bwrap
   user/PID/IPC/UTS/mount namespace probe. The probe failure is fatal; do not
   disable the security check or fall back unsandboxed.
6. bubblewrap must be non-setuid, expose --disable-userns, and pass the real
   namespace/UID/groups/CapEff probe. The image now uses Debian trixie and
   verifies the feature at build time.
7. setpriv and newuidmap must exist. The Supervisor stays root only inside the
   constrained container to start bwrap as the distinct non-root Worker UID;
   Docker capabilities remain cap-drop ALL plus SETUID/SETGID/CHOWN only.
8. No privileged mode, no docker.sock mount, no host root mount. The target
   runner and test container keep that boundary.
9. Node 22.19 TypeScript execution must work. The Dockerfile checks
   `node /opt/rsi/src/main.ts --help` at build time.
10. The manual operator prompt remains an external non-empty .txt. Target tests
    use only their temporary fixture; they never install a production prompt.

HOW TO RUN ON THE REAL TARGET

Bounded smoke (also what push CI runs):

  node rsi/scripts/linux-smoke.mjs

or explicitly:

  node rsi/scripts/linux-validation.mjs \
    --mode docker \
    --image rsi-agent:linux-validation \
    --timeout-ms 1800000 \
    --report /var/tmp/rsi-linux-validation.json

Host mode (already on a Linux target with root/bwrap; no Docker isolation layer):

  node rsi/scripts/linux-validation.mjs --mode host --report /var/tmp/rsi-host-validation.json

Optional soak, explicit and NOT part of push CI:

  node rsi/scripts/linux-soak.mjs \
    --hours 24 \
    --sample-ms 30000 \
    --report /var/tmp/rsi-linux-soak.json

A short soak is only a diagnostic. It must not be reported as a completed 24h
soak. The default is 24h and the script makes no external provider calls.

CLEANUP / DATA SAFETY

- The validation runner creates uniquely named Docker volumes/container with an
  rsi-validation prefix and uses volume-nocopy so the first baseline really
  starts from empty /data and /state rather than image-seeded directories. It
  removes only those own resources, never user volumes. --keep is opt-in.
- The soak runner uses the same isolation and an rsi-soak prefix; it removes only
  its own container/volumes/temp directories unless --keep is set.
- The target suite creates only temporary run directories under the supplied
  /data and /state volumes and removes them. It never edits the operator's
  manual prompt, production Memory, or user data.
- The host prompt is a temporary fixture file mounted read-only into the test
  container. The target test bind-mounts only rsi/test read-only.
- Logs are redacted for secret-like environment values and common key/token
  patterns. Host provider credentials are not passed into the test container.
