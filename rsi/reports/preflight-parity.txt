一、结论（先说明证据边界）

- 已把直接 CLI、Docker 部署入口和 launcher 前置检查统一到同一份可信预检实现：真实的非 setuid bwrap、`--disable-userns`、独立 host Worker UID/GID、清 supplementary groups、真实 setpriv/spawn 身份切换、PID/user/mount namespace、/proc CapEff=0、`fs.protected_hardlinks=1` 与 `fs.protected_symlinks=1` 全部失败关闭。
- 已删除 `deployment-preflight.mjs` 内第二套手写 bwrap argv/probe；该脚本不再 `spawnSync` bwrap，也不再从 Supervisor 身份直接探测。它只消费 `inspectConfiguredSandboxPreflight()` 的同一报告。
- 宿主 identity 不再用 namespace 内 `id -u` 代替：Supervisor 在沙箱外通过 `/proc/<sandboxed node pid>/status` 读取 `Uid:`/`Gid:` 四元组，并与配置 host Worker UID/GID 逐项比对；namespace 内的 uid/gid 只作为独立事实一并校验。root 启动 bwrap 导致 inside uid=10002、host uid=0 的情况会被拒绝。
- 本机完整套件实际通过：`npm run check` -> tests 326、pass 308、fail 0、skipped 18，EXIT 0，最终 `rsi checks passed.`。新增/修改的定向测试通过；strict Linux target 在 win32 仍明确失败而不是 skip。
- 这不是真实 Linux/bwrap 目标通过。本宿主 `bwrap` 不存在、Docker daemon 不可用；真实 bwrap/setpriv、/proc 宿主 UID 读取、namespace inode 比较、目标 sysctl、Docker build/up/entrypoint 与 24H soak 均未执行。mock/源码检查没有被当作目标通过。

2. `rsi/src/sandbox/preflight.ts`
   - `inspectBubblewrapRuntime(options, bwrapCommand?)` 的 options 类型改为上述接口；`BubblewrapLauncherOptions` 仍结构性兼容，launcher 无需改动即可复用同一实现。
   - 新增 `inspectConfiguredSandboxPreflight(config, options?)`：直接 CLI `--check/--start` 与 `deployment-preflight.mjs` 的唯一配置级入口。缺少 `sandbox.workerUid/workerGid` 时返回失败报告，报告 `probeExecuted=false`、`namespaceVerified=false`，不伪造通过。
   - 新增 `inspectProtectedSysctls(readSysctl?)`：只认 `1`；不可读、空值、0/其他值均失败关闭。默认读取真实 `/proc/sys/fs/...`。

   - 新增 `assessSandboxProbeFacts(facts, hostIdentity, expectations, hostIdentityError?)`：纯判定函数，集中验证 host/namespace 身份、groups、CapEff、namespace inode、mount/proc/UTS 事实。
   - 新增 `parseSandboxProbeFacts(stdout, resultMarker)`：严格解析；缺失/非法 groups、uid/gid/pid/ppid 直接判为不可用。
   - `formatPreflightReport` 新增 `protected_symlinks=...`、`probe_executed=...`、`namespace_verified=...`、`mount_verified=...`、`cap_eff_zero=...`、`supplementary_groups_cleared=...`、`host_identity_verified=...` 及 host/namespace uid/gid 与 pid 行。

   - 新增常量 `SANDBOX_RUNTIME_PROBE_READY_MARKER`、`SANDBOX_RUNTIME_PROBE_RESULT_MARKER`、`SANDBOX_RUNTIME_PROBE_HOSTNAME`。

三、强制条件与失败关闭（实现要点）

1. 实际 bwrap 与 feature：
   - 解析 realpath 后 lstat；setuid/setgid 直接失败。
   - `--version`、`--help` 失败或缺少 `--disable-userns` 直接失败；setuid 时即使 help 含该 flag 也判为不可用。
   - 不存在/不可执行的 bwrap 在 `resolveBubblewrapExecutable` 处失败，不进入 probe。

2. 独立 host Worker UID/GID：
   - 配置层要求 Supervisor UID 为 0，workerUid/workerGid 非 0 且分别不等于 Supervisor UID/GID。
   - 真实 probe 从沙箱外读取 sandboxed node 进程的 `/proc/<pid>/status`，要求 `Uid:` 四值与 `Gid:` 四值全部等于配置 Worker UID/GID。namespace 内 `uid/gid` 另行要求等于配置值；两者不能互相替代。
   - 因此“namespace 内 `id -u`=10002，但 host uid 仍是 0”会被 `host UID values ... do not all equal` 拒绝。

3. 清 supplementary groups：
   - setpriv 路径使用真实 `--clear-groups`；spawn-uid 路径由真实 probe 验证。
   - 沙箱内 `getgroups()` 必须为空或只含 Worker GID；出现 0 或其他组即失败。

4. 正确 setpriv/spawn 身份：
   - probe 与生产 launcher 使用同一命令形状；setpriv 参数为 `--reuid`、`--regid`、`--clear-groups`、`--`。
   - 不再只比较 argv；probe 真正经过该身份切换运行 bwrap。

5. namespace 与 mount：
   - 沙箱内报告 pid 与沙箱外 host pid 必须不同；`/proc/self/ns/pid`、`/proc/self/ns/user` inode 必须不同于 Supervisor 的对应 inode。
   - 必须同时满足：`/proc/self/ns/mnt` inode 不同于 Supervisor、mountinfo 存在 `/` 根挂载点、`/proc` 为 `proc` 文件系统（`PROC_SUPER_MAGIC=0x9fa0`）、UTS hostname 为 `rsi-preflight`。

6. CapEff=0：
   - 从沙箱内 `/proc/self/status` 读取 `CapEff`；缺失、非法十六进制或 BigInt 非 0 均失败。

7. sysctl：
   - `fs.protected_hardlinks` 与 `fs.protected_symlinks` 都必须可读且等于 `1`；不可读、空、0 或其他值都失败。`--config-only` 不声称已验证这两项。

8. 超时/解析/身份读取：
   - probe 有 parent 截止时间；超时明确记录 `probe timed out after Nms` 并失败。
   - stdout 超过 1 MiB、spawn 失败、非零退出、缺少 result marker、JSON 非法、Uid/Gid 不可读、找不到 sandboxed node 进程、host namespace inode 不可读，全部失败关闭。
   - probe 用 stdin 释放信号让子进程正常 exit 0；不会把“父进程主动 SIGTERM”误判为 probe 失败。

四、删除的重复 probe 与“同一结果”边界

- 删除的重复探针位于旧 `deployment-preflight.mjs`：`buildProbeArgs` 构造 `--unshare-user --disable-userns ... --ro-bind / / ... /bin/sh -c 'id -u; grep CapEff'`，再由 Supervisor 直接 `spawnSync`；它没有经过 setpriv/清补充组，且只用 `id -u` 判断 uid。该代码已完全删除。
- 当前 `deployment-preflight.mjs` 的静态检查可确认：无 `spawnSync`、无 `buildProbeArgs`、无 `--cap-drop`、无直接 `/proc` read。CLI 与 wrapper 都调用 `inspectConfiguredSandboxPreflight`/`formatPreflightReport`。
- launcher 的前置检查仍调用同一个 `inspectBubblewrapRuntime`；没有第二套 argv 或另一身份 probe。CLI、deployment wrapper、launcher 各自进程边界仍会真实重跑 probe（防止跨进程伪造报告），但三者使用同一实现、同一凭据策略、同一报告语义，不存在“一个入口通过、另一个假失败”的两套保证。
- 未引入从文件读取预检结果并直接信任的机制；跨进程不共享可篡改的缓存。

七、真实 Linux target 上的预期与剩余风险

- target harness 现在要求 `probeExecuted`、`hostIdentityVerified`、`namespaceVerified`、`mountVerified`、`capEffZero`、`supplementaryGroupsCleared` 和两个 sysctl 全部为 true；任一为 false 在 `RSI_TARGET_STRICT=1` 下直接失败，不会变绿。
- 真实 target 若失败，最可能的原因是部署侧而非预检放宽：`setpriv` 未安装/路径不同、`/proc/<bwrap>/task/.../children` 或 `/proc/<node>/status` 受 hidepid/seccomp 限制、bwrap 版本不支持 `--disable-userns`、目标 kernel sysctl 不为 1、或 target 没有 root 切换到独立 Worker UID。这些都应按失败处理，不能通过增加 capabilities、以 root 跑 Worker 或跳过 sysctl 修复。
- probe 依赖 Node 可执行路径精确出现在 sandboxed 进程 cmdline 中；当前使用 `process.execPath` 且 `--bind / /`，预期一致。若 target 的 Node 包装器改变 argv[0]，预检会失败关闭而不是降级。
- 首次 operator Pi 配置基线、真实 bwrap 下 P1-5 ro-bind、P1-8 容器 seed 等属于既有风险，不在本次修改范围内；本次未重新验收。
