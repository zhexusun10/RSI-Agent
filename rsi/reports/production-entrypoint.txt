This snapshot adds a real container-entrypoint smoke that uses the image's
default ENTRYPOINT, container-entrypoint.sh, deployment-render-config.mjs,
deployment-preflight.mjs, container-run.mjs, the production src/main.ts

The smoke itself was not executed on a Linux host in this snapshot because the

provider were exercised locally. This report does not claim CI, Docker, Linux
namespace, or production entrypoint success.

WHY THE OLD TARGET SUITE WAS INSUFFICIENT

The existing strict target suite remains unchanged and still runs with
`docker run --entrypoint node ...` over the target harness. It proves reload,
LKG, Watchdog, sleep, sandbox, and target tests, but it bypasses:

- container-entrypoint.sh and its root/process-initialization checks,
- deployment-render-config.mjs,
- deployment-preflight.mjs,
- container-run.mjs and its TERM/process-group forwarding,
- the image ENTRYPOINT/HEALTHCHECK/STOPSIGNAL contract.

The new smoke is therefore a separate suite. The old suite was not relabeled as
entrypoint evidence, and the new smoke does not bypass the entrypoint.

NEW REAL-ENTRYPOINT FLOW

1. Build or reuse the real image, then verify its bwrap version and
   --disable-userns feature.
2. Create unique, labeled Docker volumes and a unique bridge network for this
   run only. No existing user volume is reused or deleted.
3. Prepare only the test operator files on the fresh /data volume with a
   short-lived no-network helper container:
   - settings.json is the immutable image baseline settings plus
     defaultProvider="rsi-entrypoint-mock" and
     defaultModel="rsi-entrypoint-mock-model";
   - models.json is a valid operator models.json pointing at the dedicated
     local mock provider host/port;
   - auth.json is `{}`. No real token or key is used.
4. Start a fixture-only mock provider sidecar on the same dedicated network.
   It implements the OpenAI-compatible streaming chat-completions/SSE format
   consumed by the real Pi SDK. It records request tool names, system text, and
   tool results under a test-only bind mount. It is not the test subject.
5. Start the target container with no `--entrypoint` override. The image default
   ENTRYPOINT runs the real container-entrypoint.sh. The fixture prompt is
   bind-mounted read-only exactly at /run/config/system-prompt.txt.
6. A driver runs via `docker exec` only to observe the running production
   container. It does not start, replace, or wrap the Supervisor/Worker.
7. The production Supervisor starts the real bwrap Worker. The operator-selected
   model is resolved through the production worker-main.ts createProductionModel
   path using /data/pi-agent/settings.json and models.json; RSI_PROVIDER and
   RSI_MODEL are not used to inject the route.
8. The local mock drives a bounded task through the real Worker:
   - bash/read/write native tools,
   - direct-write denial probes for operator config, prompt, and Memory,
   - a brokered Memory write,
   - a workspace task write,
   - an index read for persisted read statistics,
   - an explicit sleep with a persisted future deadline.
9. The driver verifies fresh seed, index audit, file ownership/modes, plugin
   discovery, baseline/LKG digest, Worker PID/health, Memory visibility in the
   next provider request, read statistics, and sleeping health/deadline.
10. The container is stopped normally with `docker stop --time 30`. The smoke
    requires Docker State.Running=false, State.Pid=0, ExitCode=0, no OOM kill,
    and no `sending SIGKILL`/grace-expiry message.
11. A second container starts with the same /data and /state volumes. The driver
    verifies the same explicit sleep deadline and ID, Memory, workspace task,
    index read statistics, operator config, plugin generation, active digest,
    and LKG digest/generation. It then uses the existing operator
    container-control.mjs cancelSleep command and requires a new real Worker
    provider request after the wake.
12. Both containers are stopped normally again. Only the generated containers,
    network, volumes, prompt fixture, and temp evidence dirs are removed. On
    failure, redacted log tails, exit/state, error message, and stack are kept in
    the report.

ACTUAL TARGET PREMISES STILL REQUIRED

The entrypoint smoke can only pass on a Linux host with:

1. A working Docker daemon and permission to build/run containers.
2. Kernel unprivileged user namespaces; fs.protected_hardlinks=1 and
   fs.protected_symlinks=1 on the host.
3. Docker custom seccomp support and the deployment seccomp profile accepted by
   the installed Docker/libseccomp.
4. AppArmor (if present) allowing the bwrap user/PID/IPC/UTS/mount namespace
   probe.
5. bubblewrap with --disable-userns, non-setuid, plus setpriv/newuidmap in the
   image as already checked at image build.
6. Node 22.19 execution and the pinned local image contents.

Still not executed in this snapshot:

- Docker build and the real ENTRYPOINT container.
- Real bwrap mount/UID/PID namespace, seccomp/AppArmor, and operator ro-bind.
- Real Docker HEALTHCHECK, normal container stop/TERM, and volume restart.
- The local mock HTTP/SSE path from inside the actual container.
- GitHub Actions or any remote workflow.
- The optional 24-hour soak.

REMAINING LIMITATIONS / RISKS

- The new smoke is code/static/fixture-tested on Windows only; its actual Docker
  and Linux target result is blocked.
- The mock provider is a local fixture, not a real external provider. This is
  intentional: it exercises the real Pi SDK API/streaming path with no real key
  and no paid service, but it does not prove any real provider's behavior.
- The operator route is fixture models.json/settings.json; the container and
  Worker path are production code.
- CI YAML presence and local YAML parsing are not CI execution evidence.
- The strict target harness remains `--entrypoint node` by design; only the new
  suite claims entrypoint coverage.
